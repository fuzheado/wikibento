# Tapestry Project — Evaluation (primitives & cross-compatibility)

*Prepared 2026-09-08. A comparison of how WikiBento models widgets with how
the [Internet Archive's Tapestry Project](https://github.com/internetarchive/tapestry-project)
handles its primitives / basic building blocks — items, rels, groups,
presentation steps, and web sources. Motivation: assess how hard/easy it
would be to achieve cross-compatibility or design-pattern sharing between
the two projects.*

*Repo examined at HEAD (clone 2026-09-08). Companion to `TOOL-LANDSCAPE.md`
and `TOOLFLOW-ANALYSIS.md`; the WikiBento-side model is documented in
`ARCHITECTURE.md`, `WIDGET-DEVELOPMENT.md`, and `WIDGET-IDEAS.md` (Node
Algebra).*

---

## TL;DR

Both projects are **declarative documents of typed visual elements** — but
they answer different questions:

- A WikiBento **widget** is a **live query + renderer**: it polls CORS-enabled
  Wikimedia APIs on an interval, stamps its data age (freshness
  constitution), and renders into a 12-column responsive grid. No backend.
- A Tapestry **item** is a **persisted media artifact on an endless pixel
  canvas**: stored server-side, referenced by URL, with server-generated
  thumbnails. There is no refresh/liveness concept.

Forcing one runtime onto the other would distort both. **Full
cross-compatibility is not worth it.** **Pattern sharing is cheap and
valuable**, and three narrow interop seams (iframe, a Wikimedia web-source
parser upstream, an export bridge) deliver most of the value.

## Tapestry's primitives (as modeled in code)

All schema paths below are in `core/src/data-format/schemas/`.

### Items — `item.ts`

`ItemSchema` is a **Zod discriminated union on `type`** with 8 members:

| Type | Extra fields beyond the common base |
|---|---|
| `text` | HTML `text`, optional `backgroundColor` |
| `actionButton` | action (`internalLink`/`externalLink`), HTML `text` |
| `audio` | `source` URL, playback `startTime`/`stopTime` |
| `book` | `source` URL |
| `image` | `source` URL, action |
| `pdf` | `source` URL, optional `defaultPage` |
| `video` | `source` URL, playback range |
| `webpage` | `source` URL, optional `webpageType` (`youtube`/`vimeo`/`iaWayback`/`iaAudio`/`iaVideo`) |

Every item shares a common base (`commonItemProps.base`): `id`, canvas
`position` (x/y px), `size` (w/h px), `layer`, optional `title`, `notes`,
`dropShadow`, `groupId`, and a `thumbnail` — which is itself a rich
**`ImageAsset`**: a set of **renditions** `{source, format, size,
isPrimary, isAutoGenerated}` (formats include jpeg/png/ktx2; only the primary
rendition may be user-uploaded, the rest are derived/auto-generated).

### Rels — `rel.ts`

A **rel** is a first-class relation between two items: `from`/`to` endpoints,
each `{itemId, anchor (normalized 0–1 point on the item's bounding box),
arrowhead}`, plus `color` and `weight` (`light`/`medium`/`heavy`). Rendered as
lines/arrows; commentable. This is an explicit, schema'd **edge model** — but
it is an *editorial/visual* connection, not a data-dependency edge.

### Groups — `group.ts`

A logical collection of items that **behave as one**: dragging or selecting
one item drags/selects the whole group; deleting a group re-individualizes
its items. `color`/`hasBorder`/`hasBackground` styling.

### Presentation steps — `presentation-step.ts`

A guided tour **serialized as data**: a chain of steps (`type: item` or
`type: group`, linked by `prevStepId`) that focuses an item or group. The
viewer walks the chain; nothing is hardcoded UI state.

### Tapestry document — `tapestry.ts`

`{id, title, description, createdAt, items[], rels[], groups[], startView
(camera rectangle), theme (light/dark), background (hex), thumbnail}`.

**Distribution & versioning:** a Tapestry ships as a **ZIP** — `root.json`
(the TapestrySchema object) plus binaries referenced via `file:/` relative
paths. The format is **versioned v0→v7** with historical parsers kept in
`core/src/data-format/export/` — older files keep loading.

### Web sources — `core/src/web-sources/`

How arbitrary URLs become items: a **`WebSourceParser` registry**
(`matches(url) → parse(url) → construct(params)`) with concrete parsers
`youtube`, `vimeo`, `iaWayback`, `iaAudio`, `iaVideo`, plus an `unknown`
fallback. IA parsers sniff the item's media type via the archive.org API and
round-trip `start` params through the URL.

### Stack

Monorepo (NPM workspaces): `core` (Zod schema library), `core-client`
(opinionated React toolkit — canvas, media player, rich text, modals),
`client` (main app: viewer + WYSIWYG authoring), `server` (Express + Prisma +
Postgres), S3 (assets), Redis/BullMQ (jobs), optional Vault (LLM keys);
Chromium/ffmpeg/ImageMagick worker generates thumbnails. Auth: Internet
Archive or Google. Public instance: tapestries.media.

## WikiBento's model (recap for the comparison)

- **Widget** = one entry in the `WIDGET_TYPES` registry
  (`src/widgets/index.js`): `{id, name, icon, renderer (or getRenderer),
  dataSource, configFields, fetch?, transform, timeScope, defaults,
  category, intensity}`. Adding one = one registry entry + (usually) one
  fetcher in `dataSources.js`; shared renderer components do the rest.
- **Dashboard** = config-as-data JSON (`version`, `widgets`, `layout`) over a
  12-column `react-grid-layout` grid; persisted to localStorage, shared via
  URL/`?config=`. No backend; every widget fetches CORS-enabled APIs.
- **Governance**: build-gated "constitutions" — freshness (every fetching
  widget declares `refreshSeconds ≥ 30` and shows a ⏱ age footer) and
  temporal scope (resolved date range in the subtitle); provenance and
  actionability rules proposed (ISSUE-21/22).
- **Content primitives** (ISSUE-42): wiki page, image, audio, video, 3D —
  each as 1..n items with display modes. Overlaps Tapestry's media item
  union almost exactly, minus book/pdf/text, plus 3D.
- **Wiring**: no widget→widget edges today; ISSUE-50 ships a board-params
  hub (`{{param}}` interpolation + Board Controls card). Node Algebra
  taxonomy (Sources/Controllers/Transformers/Reducers/Enrichers/Routers/
  Effectors/AI-native) is the planned vocabulary for deeper wiring.

## Side-by-side

| Dimension | WikiBento | Tapestry |
|---|---|---|
| Unit of composition | Widget = live query + renderer | Item = persisted media artifact (+ rel, group, step) |
| Type system | JS registry objects; light `validateDashboard`; test-gated constitutions | Zod discriminated unions, runtime-validated everywhere |
| Format discipline | `dashboard.json`, `version: 1`, one validator | ZIP (`root.json` + `file:/` binaries); versions v0→v7 with backward parsers |
| Geometry | 12-col responsive grid; layout metadata separate from widget defs | Endless pixel canvas; x/y/w/h/layer live *in* the item; `startView` camera |
| Relations | Params hub (no edges); graph view proposed | First-class schema'd `rel` edges + groups (one-behavior selection) |
| Content types | 5 primitives + 30 data-viz widget types (cards/trends/rankings) | text, actionButton, audio, book, image, pdf, video, webpage |
| Data | Fetch-on-interval from CORS APIs; ⏱ freshness | Static URLs, archived/server-generated thumbnails; no refresh |
| Persistence | localStorage + share URL; no backend | Postgres + S3 + Redis server; auth; comments; collaboration |
| Extension point | Registry entry + fetcher (+ renderer); Node Algebra for wiring | Zod member + per-type viewer component (+ `WebSourceParser` to ingest URLs) |
| Extensibility gate | Constitutions block non-compliant widgets at build | Zod validates every parse (client + server) |

## Design patterns each could borrow

### Tapestry → WikiBento (high value)

1. **Validation-first, versioned core.** Keep-old-parsers (v0→v7) is the
   discipline WikiBento needs as share URLs age and the Ask panel / a future
   marketplace author configs. Per-widget Zod config schemas would make
   widget configs machine-checkable (validate before render; schema doubles
   as prompt context for the ISSUE-44 advisor).
2. **Presentation as data.** Kiosk/Present is currently UI state; Tapestry
   serializes guided tours. Bento-to-Bento navigation (ISSUE-35/36) and
   kiosk rotation become declarative `steps[]` in the config.
3. **Rendition-based thumbnails.** `ImageAsset` renditions
   (format/size/isPrimary) beat WikiBento's single `thumbUrl`; Commons thumb
   sizes map onto the same model.
4. **`matches/parse/construct` URL-parser registry** — the right shape for
   WikiBento's paste-a-link "list source" and URL-sniffing ambitions.
5. **Rels + groups as a rendering precedent** for the proposed read-only
   dependency-graph view (anchored endpoints, weights) and board-level
   grouping ("select/act as one").

### WikiBento → Tapestry (modest but real)

1. **Liveness with honest freshness.** Tapestry items are static; WikiBento's
   ⏱-stamped, scope-labeled live data suggests a "live item" type — and the
   discipline of showing data age rather than hiding it.
2. **"Frame a maintained tool" registry pattern** (thin fetcher + shared
   renderer) — Tapestry's web-sources only ingest *media* URLs; the pattern
   would extend to *data* sources.
3. **Constitutions as build-gated tests** — a quality gate for schema
   additions.

## Cross-compatibility: seams, ranked by difficulty

**Hard / not worth forcing:** shared runtime, shared registry, widget↔item
unification. Geometry (pixel canvas vs grid), identity (per-item UUIDs vs
positional grid slots), and semantics (persisted content vs re-querying
output — any bridge is necessarily a *snapshot*) all differ.

**Realistic seams (cheapest first):**

1. **Iframe both ways (zero code).** A Tapestry `webpage` item can embed a
   live WikiBento board (`?lean=1` / kiosk URL) today; WikiBento's `wikiPage`
   widget can frame a published tapestry if tapestries.media permits framing.
2. **Wikimedia `WebSourceParser` contributed upstream (medium-easy; highest
   genuine value).** Mirror `ia.ts`/`wayback.ts`/`video.ts`: paste a Commons
   file URL → image/video/audio item (metadata + thumbnail renditions from
   Commons APIs); paste an article URL → webpage item. This follows
   Tapestry's own extension pattern, so it is a clean upstream PR, and it
   makes Tapestry a first-class consumer of the Wikimedia commons.
3. **Export bridge (medium).** WikiBento finds data; Tapestry is the
   editorial canvas. An exporter turning any ranking/result into a `.tapestry`
   ZIP (top files → image items + rels; article lists → webpage items) is a
   natural division of labor.
4. **Shared "media row" vocabulary (tiny).** WikiBento's canonical image row
   (`{title, thumbUrl, fileUrl, caption}`) is already close to a Tapestry
   image item's `{source, thumbnail}`; a shared type would make seams 2–3
   trivial.

---

## Bottom line

- **Pattern sharing difficulty: low** — schema/versioning discipline,
  rendition model, presentation-as-data, and the URL-parser registry
  transfer without stack changes.
- **Runtime interop difficulty: high, and not worth pursuing** — the three
  seams above deliver the value without it.
- Natural follow-ups if pursued: (a) draft a Wikimedia `WebSourceParser`
  against a real Commons URL and test in Tapestry core; (b) prototype an
  export bridge from one WikiBento widget (Commons File Gallery / Article
  List) to a `.tapestry` ZIP.
